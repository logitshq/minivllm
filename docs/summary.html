用多少代码，替代了什么

七步，每步一个判据

  1. 基线。HF transformers 的 greedy 当标准答案；mlx-lm、dflash-mlx、oMLX 在这台机器上的数字当靶子。
  2. 模型前向，无 cache。fp32 对 HF fp32 逐 token 相同（logits 差 0.0001）；27B 对 mlx-lm 24/24。踩坑：mlx-community 把 RMSNorm 的 +1 烧进了权重。
  3. cache 和分块 GDN。prefill 后逐 token decode == 整句前向。踩坑：显式求逆在真实数据上炸，改前向代入。
  4. 调度器。固定槽位、无抢占、分块 prefill、decode 优先；CPU 单测 200 个随机请求。
  5. 批量 decode + Metal kernel。三个请求合批 == 各自单跑。发现 MLX 散写是整块拷贝，放弃"大池子"。
  6. server。自己写的 client 复刻 vllm bench serve；并发 32 跑通；MLX allocator 缓存限到 2 GB。
  7. DFlash2。投机的 greedy == 不投机的 greedy，128/128；GDN 状态用磁带重放回滚，1 ms。

最值钱的三个教训

  • 判据先于代码：fp32 对 fp32 逐 token 相同才算对，bf16 的分叉不要追；kernel 测试要用真实数据的统计形状。
  • Mac 不是小号 GPU：数组不可变、算力带宽比低一个量级、持续负载降频，vLLM 的三个设计假设都不成立，照抄会慢。
  • 跑分前先清机器：桌面 app 的 12 GB swap 和 allocator 的 20 GB 缓存，各自能让数字差一倍。

还没做的

  • verify 的小 M 量化矩阵乘：8 个 token 的前向 95 ms，应该接近 40；做好了投机解码从 2.2 倍到 3 倍。
  • 并发 24 到 32 的批量 decode 比 mlx-lm 静态 batch 慢 20%，原因没查。
  • server 层比裸引擎慢 13%，asyncio 的逐 token 写 SSE 待查。
  • 完整的 100 条 × 1024 协议留着夜里跑。
