# 032：190 GiB模型的加载、准入与测速是三个不同问题

2026-10-19。目标仍是同一GLM-5.3-Flash混合4/5/6-bit权重，在M5 Ultra 256 GiB上实现正确而快的专用引擎。
本轮先检验官方参考路径，未运行mini GLM，未产生速度点。文件大小约190 GiB不能证明运行时可用内存足够。

## 假设与实际尝试

前一轮加载被监控采样间隔拒绝。v3把物理样本和较慢的进程元数据检查分成两个有界监控通道，
保留220 GiB子进程、240 GiB系统、pressure正常及零新增swap的门槛；没有偷偷放宽原失败条件。
以E033真实RESTORED证据准备新计划，16项focused CPU检查在封存前后各通过一次，
实际只读prepare与回执封存后提交8c3a640，才停止外部服务、启动直接拥有的模型进程。

计划为官方EnginePool普通非lazy加载，然后4条顺序C1请求，输出上限8/32/32/32，greedy、正常EOS，
重复三次32-token请求核对原始token IDs并检查队列排空。此计划是加载/参考路径诊断，
不构成完整cache/logits数值证明、HTTP性能或Pareto成绩。

## 实测失败仍需完整恢复

物理样本0031触发实际系统swap增长：

| 观察 | 冷准入 | 触发时 |
|---|---:|---:|
| 系统swap使用量 |1,664,614,400 B|1,907,485,573 B|
| 累计Swapouts |743,802|758,682|
| 子进程物理占用 |—|195,899,489,688 B（182.45 GiB）|
| 系统物理占用 |—|218,957,332,480 B（203.92 GiB）|

swap增加约231.62 MiB，Swapouts增加14,880。子进程/系统占用尚未触及220/240 GiB上限，
压力等级仍为1，所以不能把此失败写成OOM，也不能把系统级计数全归因到某一模型的页面。
既定零增长门槛确实被违反，owner没有把它改成PASS。

取消清理期间，底层加载线程随后记录official_vlm_load:after，MLX active为204,148,686,728 B、
peak为206,754,463,624 B。然而EnginePool await没有正常返回，没有已验证loaded-engine收据，
完成请求与输出token均为0。线程返回、引擎完成准入、可正常推理是三个不同事实。

模型子进程被实际回收，监控读取已结束；driver stop/owner/recover退出码分别0/1/0。
外部服务21938恢复为34623，独立恢复审计PASS；诊断闭环审计FAIL。
精确运行时签名和暖KV缓存没有恢复。服务恢复成功不改变实验失败。

## 下一次要定位什么

先核对实际加载路径的wired limit、MLX推荐working-set、allocator缓存及临时布局转换。
区分加载阶段全局swap增长与未来稳定推理阶段swap增长；只有新的预声明实验可以改变观察合同，
旧结果保持原FAIL。是否能在加载后稳定驻留、参考请求正确完成，仍需实际验证。
即使官方参考路径可用，也不意味着我们的GLM实现已存在或领先任何对手。
