# 03 调度器：固定槽位、分块 prefill、decode 优先

日期：2026-10-13。文件：`minivllm/engine/request.py`、`minivllm/engine/scheduler.py`、`minivllm/sampling_params.py`、`tests/test_scheduler.py`。纯 Python，不碰模型。

## 资源模型：槽，不是块

vLLM 的 paged attention 把 KV 切成 16 个 token 一块，按需分配，于是需要 block 表、引用计数、前缀缓存、内存不够时的抢占和重算。
这些是 vLLM 复杂度的最大来源。

我们的选择：**每个请求整个生命周期占一个槽**，进来时就检查 `prompt + max_tokens ≤ max_len`。运行中永远不会缺内存，所以
**不需要抢占**。代价是短请求也按 max_len 预留；换来的是调度器只有一个状态：token 预算。
（第 4 步会看到，MLX 上"槽"甚至不是一块预分配的内存，而只是并发上限。）

## 每一步

```
1. 所有 prompt 已算完的在跑请求各 decode 1 个 token          ← decode 永远排在前面，不被 prefill 饿死
2. 剩余预算给 prompt 没算完的请求做分块 prefill（chunked prefill）
   先是上一步被截断的，再从等待队列按 FCFS 接新的（要有空槽）
3. 输出 SchedulerOutput：decode 列表 + prefill 块列表 [(请求, 这步算几个 token)]
```

一个 prefill 块如果刚好算完 prompt，它的最后一个位置就产出第一个 token，所以这一步要对它采样。
step 之后 `update()`：写入采样结果、推进 `num_computed_tokens`、判结束（EOS / stop / max_tokens / max_len）、释放槽。

为什么 decode 和 prefill 要混在同一步：SiliconBench 测了九个 Mac 引擎，mlx_lm 和 omlx 的 prefill 和 decode 是分开跑的，
一条长 prompt 进来所有人都停下来等；vllm-metal 混在一起跑，并发时 TTFT 最低。我们的 TTFT 上界 = 一个预算（512 token）的 prefill 时间 ≈ 2.5 s。

## 测试（CPU，0.02 s）

分块和预算：20 个 token 的 prompt、预算 8 → 8 + 8 + 4，第三块产出第一个 token；之后每步 1 个。
decode 不被饿死：r0 在 decode 时 r1 的 prefill 只能拿剩余预算。槽满时第三个请求等着。
EOS、拒绝超长请求。200 个随机长度请求、8 个槽、5% 概率吐 EOS 的模拟：全部正确结束，槽全部归还。
