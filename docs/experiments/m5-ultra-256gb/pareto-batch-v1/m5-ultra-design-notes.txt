M5 Ultra 专用路径：从实际成本出发做减法

目标：固定 Qwen3.8-27B NVFP4 与 M5 Ultra 256 GiB，减少每个输出 token 的权重读取、kernel 启动、主机往返和状态搬运。只在已验证边界启用。

1. 学 oMLX 的调度思想
本地源码 omlx/engine_core.py 的 _step_burst 把多次调度放在一次 executor 交接里，减少 GIL/事件循环往返；首块输出立即释放，并用时间预算限制响应延迟。我们的 worker 已是连续同步循环，不需要再移植这套通用异步框架。保留“减少往返、及时交付首字”的原则。额外实测官方 aggressive 模式，避免只拿默认配置作比较。

2. 学 Lithos 的固定执行计划
本地源码 runtime/src/metal_core.mm 的 Runner::run 复用 indirect command buffer，并限制在途 command buffer 数量；compiler/arena.py 按生命周期复用 scratch。我们已经用显式状态的 mx.compile 图和预打包投影复用执行计划，保留原始参数和相同算术。没有照搬其跨模型编译器、变换注册表或完整 Metal runtime，也不宣称已实现 ICB。

3. 已完成的算子简化
将 B1..B8 的投影和 GDN 融合到已验证路径。共用输入的投影合并后可少启动 kernel，GDN 的准备和状态更新保持原始归约。B12 以上合并投影会触发 MLX 不同归约路线；修正后大批次候选又有性能回退，因此不启用这一分支。专用路径默认关闭，额外派生权重约8.714 GiB，使用长度上限256。

4. 本轮已采用：一次清理一批结束的请求
旧代码在同一步中每结束一个请求，就重建一遍剩余 KV/GDN 行，形成重复状态搬运。新代码先收集完成名单，最多执行一次压缩；整批结束直接释放。模型算术、采样、调度顺序及停止条件保持原样。真实模型逐步 token/剩余缓存比对已通过，C8/C32/C64各3个独立HTTP进程已完成。采用提交 dc745bc57efaba03fd5afae7d28b3ce0625f0e62。C64吞吐中位数提高46.9%；C32提高2.95%；C8降低4.35%，这些不是逐对配对的比较。

5. 活跃批次上限是另一项独立实验
64 个客户端不意味着必须让 GPU 同时算64条序列。单独测 active cap32，全部64请求仍计入完成窗口，排队成本保留在 TTFT。它是运行配置，不是假装减少请求数。所有成功、失败和未采用候选都会保留。

数据边界：19输入/32输出、greedy、正常EOS、无前缀缓存、无草稿模型。HTTP客户端交付速率不是裸GPU TPS。Lithos官方端点只支持C1。测量中位数的Pareto覆盖不代表所有单轮结果或所有工作负载都获胜。
