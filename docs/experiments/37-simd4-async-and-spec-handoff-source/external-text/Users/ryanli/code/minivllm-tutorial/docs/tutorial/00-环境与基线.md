# 00 环境与基线

日期：2026-10-13。机器：MacBook M4 Max，40 核 GPU，48 GB 统一内存。

## 环境

```bash
cd ~/code/minivllm
uv venv .venv --python 3.13
uv pip install --python .venv/bin/python torch transformers safetensors numpy xxhash fastapi uvicorn pytest huggingface_hub
.venv/bin/hf download Qwen/Qwen3.5-0.8B
```

torch 2.14.1（MPS 可用），transformers 5.19.0。模型 1.6 GB，在 `~/.cache/huggingface/hub/models--Qwen--Qwen3.5-0.8B/`。

## MPS 摸底

| 项目 | 结果 |
|---|---|
| bf16 GEMM 4096×1024×3584 | 8.7 ms ≈ 3.5 TFLOPS |
| SDPA bf16 + GQA + causal | 可用 |

## 模型结构（Qwen3.5-0.8B，和 27B 同一架构）

24 层，hidden 1024；`layer_types` 每 4 层第 4 层是 full_attention（共 6 层），其余 18 层是 Gated DeltaNet。
full attention 8 q 头 / 2 kv 头 / head_dim 256，带 output gate，RoPE 只转前 64 维。GDN 16 k 头 / 16 v 头 / 128 维，conv kernel 4。
vocab 248320，`tie_word_embeddings=True`（27B 是 False）。参数 752M。

## 基线：HF transformers greedy（这是之后每一步要对齐的 ground truth）

HF 自己在 Mac 上也是纯 torch 跑 GDN（没有 fla / causal_conv1d），所以它既是正确性参照也是一个"没有任何工程优化"的性能参照。

prompt（chat template，`enable_thinking=False`，19 个 token）：`用一句话解释什么是 KV cache。`

```
prompt ids: [248045, 846, 198, 95826, 110827, 98682, 108829, 81726, 6297, 1710, 248046, 198, 248045, 74455, 198, 248068, 271, 248069, 271]
greedy 48 ids: [79852, 18887, 220, 98435, 98618, 103806, 95779, 103725, 111892, 95726, 108777, 111734, 98853, 3709, 96540, 96580, 96468, 100679, 96547, 96458, 98818, 95860, 99580, 103725, 104234, 98822, 9616, 1536, 220, 95793, 4997, 46662, 99131, 95772, 21966, 220, 96547, 96458, 99140, 95865, 97318, 2005, 96547, 96458, 96646, 108777, 828, 95726]
text: KV Cache 是一种用于加速大模型推理的内存缓存机制，它通过预分配显存空间来存储模型的关键状态（Key 和 Value），从而在 GPU 显存不足时实现“显存即内存”的
```

batch=1 greedy 48 token：0.44 s ≈ **110 tok/s**（含 HF 的 python 开销；0.8B bf16 权重 1.5 GB，按 ~500 GB/s 带宽的理论上限约 300 tok/s）。

## 这一步学到的

- Qwen3.5 是混合架构：3/4 的层是线性注意力（GDN），只有 1/4 是普通 attention。所以 KV cache 只有 6 层，但要额外给每个请求存 GDN 的递推状态（conv 状态 + S 矩阵），这是引擎设计上和 nano-vllm 最大的不同。
- transformers 5.x 的 `apply_chat_template(return_tensors=...)` 返回 BatchEncoding，要 `return_dict=True` 再取 `["input_ids"]`。

## Mac 原生基线：mlx-lm 0.32（mlx 0.32.3）

装在单独的 `.venv-mlx`，引擎代码不碰它（和远程把 vLLM 放在 `~/vllm-baseline` 隔离是一个意思）。

- 原生支持 Qwen3.5（`models/qwen3_5.py` + `gated_delta.py`），GDN 用的是手写 Metal kernel（`mx.fast.metal_kernel`），全注意力用 `mx.fast.scaled_dot_product_attention`。
- `mlx_lm.server` 自带 continuous batching（`BatchGenerator`，`--decode-concurrency` / `--prompt-concurrency`），Qwen3.5 的两种 cache（`KVCache`、`ArraysCache`）都可合批。
- 正确性：同一 prompt 的 greedy 前 12 个 token 和 HF 一致，之后分叉（bf16 数值路径不同，意思相同）。所以逐 token 对齐的 ground truth 仍然用 HF torch，性能对标用 mlx-lm。

`python -m mlx_lm.benchmark --model Qwen/Qwen3.5-0.8B -p 1024 -g 1024`（静态 batch，不是 serving）：

| batch | prefill tok/s | decode tok/s | 峰值内存 |
|---|---|---|---|
| 1 | 9292 | 220 | 2.5 GB |
| 32 | 10137 | 1812 | 5.3 GB |

对比 HF torch MPS batch 1 的 110 tok/s：MLX 单流快 2 倍，合批后再 8 倍。本地引擎要"持平"的对象就是这张表，以及 `mlx_lm.server` 在 1024/1024/100/并发 32 下的 serving 数字（下一步测）。

## 补：nvfp4 开发模型与 27B 目标（同日稍晚）

决定做 Qwen3.8-27B 之后，把 0.8B 也转成和 27B 一样的 nvfp4 格式做开发模型：

```bash
.venv-mlx/bin/python -m mlx_lm.convert --hf-path Qwen/Qwen3.5-0.8B --mlx-path models/Qwen3.5-0.8B-nvfp4 -q --q-mode nvfp4 --q-bits 4 --q-group-size 16
```

423 MB，4.508 bit/weight。`mlx_lm.benchmark` 1024/1024：batch 1 → 441 tok/s，batch 32 → 2614 tok/s（bf16 是 220 / 1812，4 bit 权重少读一半多内存，decode 就快一倍）。

27B：`mlx-community/Qwen3.8-27B-nvfp4` 16.1 GB，config 里 `quantization = {group_size 16, bits 4, mode nvfp4}`，64 层、48 GDN + 16 full attention、24/4 头、GDN 16/48 头。MLX `device_info()` 报告推荐工作集 37.4 GB。

## 补：27B 实测，以及投机解码在这台 Mac 上能赚多少

`mlx_lm.benchmark` 27B nvfp4（p=256，g=64）：batch 1 → **28.8 tok/s**（34.7 ms/步，16 GB 权重 ÷ 34.7 ms ≈ 460 GB/s，已经贴着带宽上限）。batch 2/4/8/16 → 45 / 74 / 76 / 68 tok/s：合批到 8 以上吞吐就不涨了，说明 mlx-lm 的 batch 路径在 8 之后变成算力或 kernel 瓶颈。

投机解码的收益取决于"一步里多验证几个 token 要多花多少时间"。直接测：单条序列、prefill 256 之后，一次前向送 k 个 token（就是 verify 的形状）：

| k（一步验证的 token 数） | ms/步 | 相对 k=1 |
|---|---|---|
| 1 | 40.7 | 1.00 |
| 2 | 39.7 | 0.98 |
| 4 | 45.2 | 1.11 |
| 5 | 53.6 | 1.32 |
| 8 | 84.0 | 2.06 |
| 16 | 154.1 | 3.79 |

到 4 个 token 几乎免费，5 个开始要加钱，8 个翻倍。这就是 Mac 和 H200 的差别：H200 上验证 8 个 token 和 1 个差不多（算力/带宽比高一个量级），所以 DFlash2 在 GPU 上用 block 8；oMLX 在 Mac 上默认 block 5，Weschera 在 M4 Max 上测 MTP k=3 最优，都是同一个原因。

单独测 `mx.quantized_matmul`（27B MLP 形状 5120×17408）：nvfp4 M=1 → 0.25 ms，M=8 → 0.37 ms，M=16 → 0.65 ms。GEMM 本身 8 个 token 只贵 50%，整模型却贵一倍，说明多出来的时间在 GDN / attention / 框架开销上，不在矩阵乘。这是我们自己的引擎能比 mlx-lm 快的空间。

按 DFlash2 model card 的接受长度（block 8 时每步 4.1–5.5 个 token）估：block 8 → 4.5 ÷ (84 + 草稿 ~8) ms ≈ 49 tok/s；block 5 → 约 3.5 ÷ 60 ms ≈ 58 tok/s；换成专门的小 M kernel 把 8 个 token 压到 ~50 ms → 约 78 tok/s。所以 M4 Max 上 27B 的现实目标是 **28.8 → 55–75 tok/s（2–2.6×）**。

### Mac 上已有的"vLLM"们（第 5、6 步的对标对象）

| 项目 | 是什么 | 已发表的数字 |
|---|---|---|
| [oMLX](https://github.com/jundot/omlx)（22.8k star） | mlx-lm BatchGenerator 之上的 continuous batching + vLLM 式 paged KV（block、CoW、prefix 共享）+ SSD 冷层 + 原生 MTP + DFlash + ANE prefill | Qwen3.8-27B oQ4e + MTP k=3，M4 Max：**53 tok/s 文 / 72 tok/s 代码**，MTP 关掉 24.6 tok/s（[Weschera 的复现](https://github.com/Weschera/Qwen3.8-27B-oMLX-MTP-Mac)） |
| [dflash-mlx](https://github.com/bstnxbt/dflash-mlx) | DFlash / DFlash2 的 MLX 实现：verify 专用小 M int4 Metal kernel、GDN 状态"磁带回放"回滚、L1/L2 前缀缓存 | Qwen3.5-27B-4bit，M5 Max：33.5 → 79 tok/s（2.37×，1K 上下文），8K 上下文掉到 1.34× |

结论：本地的 SOTA 门槛是 oMLX / dflash-mlx 这一档，M4 Max 上 27B 单流 55–72 tok/s。我们的引擎第 5 步对标 `mlx_lm.server` 和 oMLX 的并发吞吐，第 6 步对标 dflash-mlx 的单流速度（`dflash benchmark --model mlx-community/Qwen3.8-27B-4bit`，已装在 `.venv-mlx`，4bit checkpoint 和 `z-lab/Qwen3.8-27B-DFlash2` 草稿在下载）。

## 基线结果（2026-10-13 晚，M4 Max 48 GB，其他 app 全部退出）

跑分脚本 `bench/run_baselines.sh`，client `bench/bench_serve.py`（协议和远程那条 `vllm bench serve` 一致，缩短为 32 条 prompt、1024 进 256 出，因为 mlx-lm 跑完整协议要两小时）。

| 场景 | 基线 | 结果 | 备注 |
|---|---|---|---|
| 单流 AR，27B nvfp4 | mlx_lm.benchmark | 24.1 到 28.8 tok/s | 同一命令两次相差 15%，热/频率波动，以后每个数至少跑 3 次取中位 |
| 单流 AR，27B 4bit affine | mlx_lm.benchmark | 25.9 到 29.6 tok/s | decode 和 nvfp4 一样快；**prefill 241 vs 138 tok/s**，MLX 的 nvfp4 大 M 路径慢 40% |
| 单流 + DFlash2，27B 4bit，block 8 | dflash-mlx（GitHub main） | 59.9 tok/s（2.02×） | 接受率 70.5%，512 token 数学题 |
| 单流 + DFlash2，27B 4bit，**block 5** | dflash-mlx | **64.2 tok/s（2.17×）** | block 5 比 8 快，和前面算的 Mac 平衡点一致 |
| 并发 8，32 条，1024/256 | mlx_lm.server | 端到端 27.8 tok/s；decode 阶段 TPOT 165 ms → 48 tok/s；TTFT 平均 32 s | 峰值 17 GB，无 swap。prefill 不和 decode 重叠，8 条一起排队 prefill 时所有人都在等 |
| 并发 32，32 条，1024/256 | mlx_lm.server | **跑不了**：进程 38 GB，Metal 报 Insufficient Memory，生成线程死亡，10 条失败 | 理论需要约 25 GB，它多用了 13 GB |

踩的坑：
- 第一次跑并发 32 时桌面上开着十几个 app，系统 swap 12 GB，整机 20 tok/s，全是换页拖的。跑分前要退出其他 app，并且记录 swap 和进程占用（脚本里的 `memline`）。
- `mlx_lm.server` 默认把跑完的请求的 KV 留在 LRU prompt cache 里复用，跑分要 `--prompt-cache-bytes 1` 关掉；`--prompt-concurrency 8` 的 prefill 中间激活很大，改成 2。
- PyPI 的 dflash-mlx 0.1.8（5 月）不认 DFlash2 的 config（`rope_parameters`、`dflash_config.block_size`），要装 GitHub main。
- 静态 `mlx_lm.benchmark` batch 8 是 76 tok/s，server 里同样 batch 8 的 decode 只有 48 tok/s：server 每步多了约 60 ms 的逐流 Python 开销（detokenize、JSON、socket）。

### 由此定下来的本地目标

1. 单流：带 DFlash2 ≥ 64 tok/s（dflash-mlx block 5），AR 不低于 29 tok/s。
2. 并发 32：**能跑**（内存按账面 25 GB 分配，不多占），decode 阶段吞吐 > 48 tok/s，prefill 分块和 decode 混在同一步里，TTFT 不能是几十秒。
3. prefill：nvfp4 的大 M GEMM 要追上 affine 4bit 的 241 tok/s，或者 MLP 用 affine、attention 用 nvfp4 混着来。

## 别人在 48 GB Mac 上的结果，和我们的数字对一对

| 来源 | 机器 | 配置 | 他们的数字 | 我们的 |
|---|---|---|---|---|
| [oMLX 社区跑分](https://omlx.ai/benchmarks/performance/p3kbtfg6) | **M4 Max 40c，48 GB**（和这台一样） | 27B 6-bit，1k 上下文，单流 | prefill 243，decode 20.2 tok/s，峰值 24.5 GB | 4-bit/nvfp4 decode 24–29（权重 16 vs 24 GB，按带宽换算 6-bit 约 20，一致） |
| [HN 帖子](https://news.ycombinator.com/item?id=49403412) | M4 Pro 48 GB | 4-bit + MTP + 4-bit KV | 13 tok/s 裸跑，20 带 MTP | M4 Pro 带宽是 Max 一半，13 ↔ 28 一致 |
| 同上 | M4 Max 128 GB | 27B + 投机解码 | 59.5 tok/s | DFlash2 block 5：64.2 |
| [vikesh-c 的 48 GB 配方](https://github.com/vikesh-c/Qwen-3.8-27B-oMLX) | M5 Pro 48 GB | 4-bit + DFlash2 block 5 + 8-bit KV，128k 上下文 | decode 18–38 tok/s，常驻 23 GB，**prefill 瞬时逼近 38 GB 硬水位** | 我们 mlx-lm 并发 32 正是在 38 GB 撞死 |
| [SiliconBench 论文](https://arxiv.org/abs/2609.19169)（2026-09，Penn State + EXO） | M5 Pro 64 GB | 27B 4-bit，并发 1/2/4，四个引擎 | mlx_lm 只完成 23–31/100（Metal OOM collapse）；vllm-metal 吞吐随并发上升、c=4 时 TTFT 最低；omlx 一次只 prefill 一条 | 和我们看到的 mlx-lm 现象一致 |

结论：
1. 单流和投机解码的数字都复现了，偏差在量化位宽和带宽换算的范围内。
2. **没有人发表过 27B 在 48 GB 上并发 8 以上的结果**。SiliconBench 最多测到并发 4，而且是 64 GB 机器。并发 32 装进 48 GB 是空白，也是我们引擎最清楚的卖点。
3. SiliconBench 的引擎架构表把问题点得很准：mlx_lm 是 padded batch + 连续 KV + prefill/decode 分开跑 + 内存无上限；vllm-metal 是 packed tokens + paged KV + prefill/decode 同一步 + 显式内存上限，所以它并发时 TTFT 最低。这就是远程契约里 V1 调度器 + paged KV 那套设计，论文替我们验证了方向。
