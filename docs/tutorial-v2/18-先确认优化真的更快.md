# 18：先确认优化真的更快

这一章记录两个没有进入引擎的实验。它教的是如何拒绝一个看起来合理、数值也通过的优化。当前26个引擎源码文件保持原样，V19默认关闭；本章没有新增生产开关。

## 1. 从同一个输入开始

GDN 的 qkv/z/b/a 四个投影读取同一行 hidden state；MLP 的 gate/up 两个投影也是如此。直觉上，把它们合为一次量化矩阵乘可能减少调用开销。

原路径的关键代码是：

```python
qkv = in_proj_qkv(x)
z = in_proj_z(x)
b = in_proj_b(x)
a = in_proj_a(x)
# MLP 则是 gate = gate_proj(x); up = up_proj(x)
```

对于这个 checkpoint，输入 x 为 BF16[1,5120]。NVFP4 每个 uint32 存8个4-bit值，每16个值有一个uint8 scale：weight 是[N,640]，scales 是[N,320]。

所以可以保留每一行的原字节，把不同投影的输出行按原顺序排在一起：

```text
GDN: [qkv 10240行 | z 6144行 | b 48行 | a 48行]
MLP: [gate 17408行 | up 17408行]
```

加载期连接权重和 scales；运行时做一次 QMM，再按原边界 split 输出。这里没有改变 K 方向的量化组。

```python
w = mx.concatenate([op.weight for op in ops], axis=0)
s = mx.concatenate([op.scales for op in ops], axis=0)
mx.eval(w, s)
y = mx.quantized_matmul(x, w, s, None, transpose=True,
                       group_size=16, bits=4, mode="nvfp4")
boundaries = [10240, 16384, 16432]  # MLP 对应 [17408]
outputs = tuple(mx.split(y, boundaries, axis=-1))
```

这是省略资格判断的节选；[参考包](../experiments/18-projection-packing/README.md)保留真实 generic helper。它拒绝非自有 Linear、subclass、混 K/量化配置/dtype、缺 scales 或带 bias 的组。后端固定默认GPU、MLX0.32.3及受测legacy Metal，运行输入只接受BF16单行；未知条件回原路径。

## 2. 拼接时也会付出成本

连接本身需要新的 slab。若原投影仍持有旧权重，再让 helper持有一整套新权重，推理前就多占了一套内存。

实验先 eval slab，再创建并 eval 连续行 slices，整组成功后才把原 Linear 重绑到这些 slices。prefill/B2/B4 等 fallback继续调用原 Linear；旧权重不得藏在 loader字典、闭包或cache中。替换参数或改量化元数据会让 helper失效，不能继续使用旧 slab。

CPU doubles能够核对“代码没有显式保留旧数组”；它不能证明 MLX slice共享物理allocation。selected3实测 active-memory下降也只属于所选三组，不能推断全部模型的峰值或物理RSS。

## 3. 三个问题需要三份证据

| 问题 | 本次验证 | 不能替代什么 |
|---|---|---|
| 权重存储是否保留？ | U32/U8原输出行连接、无重新量化 | 有限精度输出资格 |
| 输出是否相同？ | 每段finite/shape/dtype/BF16原始bytes零差 | 性能收益 |
| 调用是否更快？ | 两条路径消费全部输出的同步host wall配对 | 完整模型吞吐、cache或E2E资格 |

N从原大小变为总行数，可能改变底层 kernel选择、tile、split-K或累加树。数学上相同的线性映射不能自动获得逐字节相同的资格。反过来，输出逐字节相同也不保证更快；总权重读取量没有减少，还存在构图、分派与split成本。

## 4. 为什么旧的21.9%不能用

旧 GDN AC 实验中，拼接路径中位时间低21.9395%，但只赢3/5对。AB顺序三次全胜，BA顺序两次全败；每一对都是第二个 block更快。

检查 driver后发现，首 block前有慢的资源probe，次 block前只有CPU输出hash。准备过程不对称，因此位置和实现混在一起。具体是时钟、cache还是其他状态造成，现有证据无法确定。

正确的处理是保留旧STOP和所有负对，另写新实验协议；不能只保留AB、把3/5改成够用，也不能把猜测的物理原因写成结论。

## 5. 给两条路径相同的准备

新driver在每个block前执行相同次数prime，随后同步；计时只覆盖固定次数的完整调用与最终同步。两块结束后才转CPU、算hash、写JSON和probe。

```python
for j in range(prime):
    outputs = invoke(variant, j)   # invoke内eval所有段
mx.synchronize()
start = time.perf_counter_ns()
for j in range(repeats):
    outputs = invoke(variant, j)
mx.synchronize()
end = time.perf_counter_ns()
```

固定前AA/BB→3个AB和3个BA→后AA/BB。AA、BB比较同一路径的两个位置：若它们也不同，就不能把AB差异全归因于优化。原始起止时间、prime和全部十对都保留。

v20固定prime16/repeat64；位置控制虽通过当时宽门，BB中位slot2/slot1仍为0.902185。性能仅改善0.147238%、赢4/6，未达到跑前固定的5%和至少5/6门，因此STOP。

v21换成独立的MLP方向，跑前固定prime128/repeat512，控制门为中位[0.98,1.02]且每对[0.95,1.05]；不能把这套新门追溯套在旧数据上。

## 6. 控制通过了，仍然可以没有收益

| 新实验，Battery | 原独立Linear A | 拼接QMM B | B的表现 |
|---|---:|---:|---|
| v20 GDN，三个层/12段 | 466.4866484μs | 465.7998047μs | +0.147238%，4/6胜，STOP |
| v21 MLP，三个层/6段 | 761.2115898μs | 762.1476240μs | 慢0.122966%，3/6胜，STOP |

v21的AA为1.003758/1.000395、BB为0.995425/0.994880，严格位置控制通过。此时更清楚的结论是：这次选定局部输入和后端上，没有达到预声明收益门。

v20的120条bytes记录来自8个distinct synthetic输入与B2/B4 fallback；v21的66条记录还加入各层1个历史真实MLP输入。三个真实文件是旧V17/gates ON首次normal decode保存的BF16[1,5120]，不是本轮新跑模型得到的；计时池仍只用8个synthetic。

两次新测试都只按safetensors header定位目标tensor，再memmap单tensor、显式复制脱离映射、转MLX并eval。GDN选择0/32/62层，MLP选择0/32/63层；没有加载27B完整模型。MLP三个组payload约300.81MB。
