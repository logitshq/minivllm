# A2：怎样确认加速来自这次改动

[六篇目录](README.md) · [上一节 A1](a1-timing-boundaries.md) · [下一节 B1](b1-postconv.md)

接着 [A1](a1-timing-boundaries.md)，假设已找到一个值得改的 kernel。A 是原实现，B 是候选。只跑一次 A，再跑一次 B，能说明 B 更快吗？机器状态、预热、缓存和运行顺序都可能改变结果。

**baseline → 新做法：** 从单次先后比较，改为一次只改变一个因素，并平衡顺序。以下是实验设计示意，不是可直接执行的驱动：

```text
先完成正确性检查、相同预热，再测：
AB、BA、AB、BA、AB、BA
另做：AA、BB                  ← 同一实现也会波动多少？
```

AB 是先原实现、后候选；BA 反过来。AA/BB 用同一个实现重复运行，帮助识别顺序漂移。二者都快一点并不自动证明 B 有效：应把变化与同实现的波动比较。资源探针、输出 hash 等操作也须对称放置；原投影拼接实验把 hash 移到整对结束后，避免只扰动其中一边。

一个真实反例是旧18章：早期结果看似延迟降低约 21.94%，但五个第二运行块都更快，AB 三次赢、BA 没赢。这个结果不足以归因于拼接；重新平衡后，GDN 拼接约快 0.15%，MLP 拼接还略慢。不能把第一次的大数字继续写进收益表。

**采用门槛先写，看到结果后不改。** 旧19章局部 QMV 试验规定中位改善至少 5%、至少赢 5/6 对，并满足正确性及控制条件。候选赢了 5/6 对，中位只快约 0.21%，因此没有采用。这里的 5% 是该实验的工程门槛，不是通用统计定律，也不是后来所有服务测量的统一标准。

旧35章还保留了“6/6 都赢，但只快约 0.59%”以及“反而慢约65%”的候选。失败记录告诉我们哪些方向在这个形状、精度和机器上不值得继续；它们也是教程内容。

**保持不变：** 模型、输入、数学约定、计时边界及退出条件。数值通过和性能通过分开记录；局部通过后还要测完整请求。

**理解题：** 若 AB 总是 B 赢、BA 总是 A 赢，最先应该怀疑什么？
