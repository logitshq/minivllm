# 12：从同步到流水线，再到算子融合

第十一章让我们知道怎样比较速度。这一章开始改执行过程：先让 GPU 接着算下一步，再把 GDN 的列分成小组，最后编译已有的 norm 表达式。每个小步骤各有一个 commit，旧版本继续可读。

当前固定版本是 `tutorial-12-v1`。第一步 `tutorial-12-pipeline` 基于 `tutorial-format-v1`，替换 [model_runner.py](../../tutorial_code/miniengine/engine/model_runner.py)；第二步 `tutorial-12-tiling` 只继续替换 [gdn_metal.py](../../tutorial_code/miniengine/kernels/gdn_metal.py)；第三步再替换 [layers.py](../../tutorial_code/miniengine/model/layers.py)。模型、量化与调度器沿用上一章，三步各有独立 commit。

## 第一步：当前 token 交给 CPU 前，先提交下一轮

### 问题：GPU 的下一轮要等 CPU 绕一圈

上一版每次 decode 的顺序是下面这样。节选省略了投机与 prefill 分支：

```python
tokens = mx.array([r.output_token_ids[-1] for r in decode])
logits = self.model(tokens, ctx)
toks = sample(logits, [r.sampling for r in decode])
mx.eval(toks, *self.batch.arrays())
ids = toks.tolist()
# run() 返回 IDs；scheduler.update() 更新历史、停止条件和位置。
# 下一次 run() 再从 CPU 历史创建 tokens。
```

`tolist()` 要等设备结果。CPU 随后更新请求、做调度、构建下一轮图，这段时间下一轮模型工作还没有提交。只把 `eval` 改成 `async_eval`，接着马上 `tolist()`，仍会在原来的依赖处等待。

### 新代码：设备上的 token 直接成为下一轮输入

新 runner 先异步提交当前轮，再用设备上的 `toks` 建下一轮图。这里展示提前提交的核心，完整 eligibility 判断在源码中：

```python
mx.async_eval(toks, *self.batch.arrays())
layers = [BatchKV(l.K[:], l.V[:]) if isinstance(l, BatchKV)
          else BatchState(l.conv, l.S) for l in self.batch.layers]
next_pos = [p + 1 for p in positions]
next_ctx = ForwardContext("decode", layers, positions=mx.array(next_pos),
                          lens=mx.array([p + 1 for p in next_pos]),
                          max_len=max(next_pos) + 1)
next_logits = self.model(toks.astype(mx.int32), next_ctx)
next_toks = sample(next_logits, [r.sampling for r in decode])
mx.async_eval(next_toks, *arrays)
# arrays 是 future layers 的 K/V 或 conv/S；结果暂存在 self._ahead。
```

当前轮仍经过 `mx.eval` 和 `tolist()` 返回。变化在于下一轮工作已经排到设备上，CPU 处理当前结果时，GPU 可以继续沿依赖计算：

\[
\mathrm{logits}_t \to \mathrm{token}_t \to \mathrm{model}_{t+1}
\]

这是一轮提前提交，使用同一个目标模型，没有 drafter。token 的自回归依赖仍然保留。我们从 oMLX 所用的 `mlx_lm` 生成循环学习这种提交顺序，再修改自己的 runner。

### 实际 oMLX 普通路径里能看到什么

当时实际安装的 `mlx_lm/generate.py` 中，`GenerationBatch._step` 在1355行开始。[已归档的源码学习记录](../../tutorial_code/examples/chapter12-optimization-screen.json) 的 `source_walkthrough.source_text` 保存了调用链、原安装路径与以下摘录，并附该记录的 SHA256；这里不链接读者 checkout 中未安装的 `.artifacts` 文件。下面节选1362—1367与1403—1411，省略了中间的logits处理与采样：

```python
self._current_tokens = self._next_tokens
inputs = self._current_tokens
logits = self.model(inputs[:, None], cache=self.prompt_cache)
# ... logits 处理和采样，得到 sampled ...
self._next_tokens = sampled
mx.async_eval(self._next_tokens, self._next_logprobs, token_context)
mx.eval(inputs, self._current_logprobs)
inputs = inputs.tolist()
```

`inputs`来自上次的设备数组。下一次采样先提交，当前 token 随后读回。正常调用从 oMLX Scheduler 的 `next_generated()`，经 `BatchGenerator`、`GenerationBatch.next()` 到 `_step()`；VLM adapter 最终调用普通 language model。这里对应已有 oMLX 的普通生成路径，不是独立的 `fused_greedy_decode` 接口。

我们学习这个顺序，但自己的同步 `run()` 还要处理调度变化与 future cache 提交，因此继续使用上一节的独立句柄和快照。

### 为什么 cache 必须有“当前”和“未来”两份句柄

当前轮消费输入后形成 committed cache；提前轮消费刚采样的 token 后形成 future cache。只有下一次调度仍然匹配，future 才能替换 committed。

`BatchKV(l.K[:], l.V[:])` 创建新的 MLX array 对象句柄。它可以共享已求值的存储；重点是隔开对象。`mx.array` 的索引写入会替换对象持有的图，若直接使用 `BatchKV(l.K, l.V)`，未来写入会把当前句柄也推进一步。首次候选就曾出现 IDs 相同、committed cache hash 不同；这处修正保留在本提交中。

GDN 用独立 `BatchState` holder，原来的 `_decode` 会给它重新赋值 conv/S。它的未来状态也留在 future holder 中。

### 下一次调度怎样决定复用还是丢弃

比较键不能只看 request IDs 和位置。调用方可以修改采样参数或输入历史，因此本实现还保存完整采样快照与最新输入 token：

```python
sampling_key = tuple((r.sampling.temperature, r.sampling.top_p,
                      r.sampling.top_k, r.sampling.max_tokens,
                      r.sampling.ignore_eos, tuple(r.sampling.stop_token_ids))
                     for r in decode)
key = ([r.req_id for r in decode], positions, sampling_key,
       tuple(r.output_token_ids[-1] for r in decode))
if self._ahead is not None and self._ahead[0] == key:
    _, toks, layers = self._ahead
    self.batch.layers = layers
```

提前结果的输入快照在当前 token 交付后补齐，使用这次已经读回的 IDs，没有额外读回未来 token。下一轮 key 不匹配，就从 committed cache 重新计算。

提前提交只用于无 drafter、全 greedy、当轮没有 prefill、每个请求仍有输出与上下文余量的 decode。批次 rebuild、drop 或清空会丢弃 `_ahead`。当前 token 若是 EOS/stop，已经排队的未来结果也丢弃，调度器只看已交付的 token。

混合 prefill 时，可以采用已有且匹配的提前结果作为本轮 decode，但不再提交它的下一轮。新请求进入 DecodeBatch 后会触发 rebuild，保证行顺序与 cache 对得上。

## 第二步：GDN 每组只管32列，归约顺序保持不变

### 问题：一整头放在一个大线程组里

原 GDN decode kernel 的状态是 `S[B, Hv, Dk, Dv]`。这次27B模型使用 `Hv=48`、`Dk=Dv=128`。每个 value 列 v 的递推只读写这一列：

\[
\mathrm{kv}_v=\hat{k}^{\mathsf T}S_{:,v},\qquad
\delta_v=(v_v-e^g\mathrm{kv}_v)\beta
\]

\[
S'_{:,v}=e^g S_{:,v}+\hat{k}\delta_v,\qquad
 o_v=\hat{q}^{\mathsf T}S'_{:,v}
\]

这里的 \(\hat q\) 已包含原代码的归一化与 \(D_k^{-1/2}\) 缩放。不同 value 列之间没有状态依赖，所以可以按列分组。最终的 gated RMSNorm 要读整头输出，仍留在后面的独立运算里。

原版一组覆盖整个头：128列乘 `SPLIT=4`，共512线程；B1只有48组。每列的四个线程各算连续32行 K，然后按第0、1、2、3段的固定顺序归约。原地址与发射方式是：

```text
dv = thread_position_in_threadgroup.x
red[sp * Dv + dv] = kv
kv = sum_in_order(red[i * Dv + dv], i=0..3)
threadgroup = (Dv, SPLIT, 1)
grid = (Dv, Hv * SPLIT, B)
```

### 新代码：切列，保留完整状态的行跨度

本提交设 `VALUE_TILE=32`，一个线程组只处理32列：

```text
dv_local = thread_position_in_threadgroup.x
dv = threadgroup_position_in_grid.x * VALUE_TILE + dv_local
red[sp * VALUE_TILE + dv_local] = kv
kv = sum_in_order(red[i * VALUE_TILE + dv_local], i=0..3)
threadgroup = (VALUE_TILE, SPLIT, 1)
grid = (Dv, Hv * SPLIT, B)
```

全局状态地址仍是 `base + d * Dv + dv`，其中 Dv 仍为完整头宽度128；只把共享归约数组的跨度改为32。若把全局状态跨度也改成32，就会读写别的列。

| B1 / Hv48 / Dv128 | 原版 | 本步 |
|---|---:|---:|
| 线程组数 | 48 | 192 |
| 每组线程数 | 512 | 128 |
| 每组共享归约数组 | 2048 bytes | 512 bytes |

更多较小的组给 GPU 调度另一种选择，是否改善完整请求还要测。总状态字节与递推工作没有减少。

### 为什么没有把 Lithos 的归约代码搬进来

我们从 [Lithos 固定版本的列状态布局](https://github.com/lithos-ai/lithos-metal/blob/5485ad6bac0a5649d66a347f3e01a655ea29d937/kernels/common/gdn_mixer.metal) 学到列可以独立拥有状态。它的跨距 K 行、`simd_sum` 和 FMA 排列与我们不同；直接替换会改变浮点运算顺序。

上游 `gdn_mixer` 的实际状态地址（428—434行节选，省略外层循环）也显示了这种所有权：

```cpp
float S[KR][SL];
for (uint i = 0; i < KR; i++) {
    device const float* state = (t0 == 0u) ? rec_in : (device const float*)rec_out;
    for (uint j = 0; j < SL; j++)
        S[i][j] = state[((ulong)(h * DK + lane + 32u * i)) * DV + s * SL + j];
}
```

`s*SL+j`决定此 slice 的 value 列，`lane+32*i`决定该 lane 的 K 行；寄存器里的 `S[KR][SL]`只持有这个 slice。自己的版本借用列可分这一性质，保留原来的连续 K 段布局。

自己的 SPLIT4 连续行循环、FP32 表达式、归一化、缩放、exp，以及两次四段归约都保留。三次 barrier 也保留：先等 kv 各段写完；再等所有线程读完旧归约数组；最后等 readout 各段写完。每个状态元素与输出列仍有唯一 writer，列组之间无需归约。

分组使用普通 Metal threadgroup 内存与线程，可用于实际 Apple9。Lithos 的 T1 整头融合 norm 分支有另一种组布局；M5/Apple10 的自动融合 recipe 也不能当作本机 M4 的运行路径。

### 非32倍数的宽度继续使用原内核

```python
tiled = Dv % VALUE_TILE == 0
kernel = _kernel if tiled else _legacy_kernel
```

`_legacy_source` 从同一模板还原原来的 dv 与共享数组地址，非32倍数的受支持 Dv 继续用原尺寸的组。原来的 `Dk % 4`、`Dv <= 128` 等形状限制保留，没有在 barrier 前插入“越界线程提前 return”。

## 第三步：编译已有 norm 表达式，保留舍入位置

### 问题：很多小运算反复形成执行图

每个模型层都调用 norm。原来在 `RMSNorm.__call__` 中逐次构建 cast、平方、mean、rsqrt 与乘法：

```python
w = 1.0 + self.weight if self.zero_centered else self.weight
xf = x.astype(mx.float32)
y = xf * mx.rsqrt(mx.mean(xf * xf, axis=-1, keepdims=True) + self.eps)
return (y * w).astype(x.dtype)
```

GatedRMSNorm 还会计算 gate 的 SiLU，再乘到 norm 输出上。计算本身不变，但整段函数可以交给 MLX 编译器优化执行图与可融合的小运算。本章没有假设它一定变成单个 Metal dispatch。

### 新代码：原表达式搬入纯函数

```python
@partial(mx.compile, shapeless=True)
def _rms_norm_explicit(x, w, eps):
    xf = x.astype(mx.float32)
    y = xf * mx.rsqrt(mx.mean(xf * xf, axis=-1, keepdims=True) + eps)
    return (y * w).astype(x.dtype)
```

类仍在原位置计算 zero-centered weight，只把 `return` 换成 `_rms_norm_explicit(x, w, self.eps)`。GatedRMSNorm 的新 helper 同样保留原表达式：

```python
@partial(mx.compile, shapeless=True)
def _gated_rms_norm_explicit(x, w, gate, eps):
    xf = x.astype(mx.float32)
    y = (xf * mx.rsqrt(mx.mean(xf * xf, axis=-1, keepdims=True) + eps) * w).astype(x.dtype)
    return y * nn.silu(gate.astype(mx.float32)).astype(y.dtype)
```

普通 norm 的 norm/weight 计算保持 FP32，最后回到输入 dtype。本例是BF16。gated norm 的 norm/weight 后先回到BF16；gate在FP32做SiLU，再回到BF16；最后的输出乘法仍在BF16。这些 cast 位置决定舍入，不能仅凭实数公式相同就删掉。

### 为什么借鉴“融合”，仍要使用自己的算式

oMLX 实际启用的 Qwen3.5 B1/T1 前处理在 `qwen35_gdn_prework.py`：`gdn_prework_fused` 769行，资格判断1864行，普通模型2065行调用它。它融合 conv/SiLU、拆头、q/k norm/scale 与原始 conv tail；recurrence、最终 gated norm 与输出 projection 仍在后面。

其 Metal 卷积111—120行的关键算式是：

```cpp
acc += float(xv) * float(conv_w[channel * 4 + tap]);
const T conv = T(acc);
```

它先用FP32累加，再转回T。自己的原卷积先产生BF16乘积，每个tap累加也回到BF16，因此不能直接把这两行换进来。先做本步 norm 表达式编译，能隔离一种变化。额外的 decode prework 编译候选有独立记录，但系统筛选的边际变化约0.9%，没有稳定增益证据，所以没有合入本章。

已有 norm 微实验覆盖 `[1,5120]`、`[4,5120]`、`[1,24,256]` 与 `[1,48,128]`。普通和gated norm 共8个比较均数值逐位一致、最大绝对差0。记录的160步串行 norm 时间只属于随机输入的微实验，不能给它归因一个全模型或HTTP加速百分比。

七个案例的已记录输出和cache检查点均相同，每个案例结束后都清空请求、staging、batch与ahead，再复用runner生成5个token。logits/cache hash对FP32转换后的数值与shape计算；它证明这些有限路径的数值一致，不证明任意dtype/layout等价。late-chunked的短B2区间由完整logits记录覆盖，没有宣称该区间逐步都有cache hash。

cap1/cap2、精确max_len、显式idle、启用drafter和任意外部行重排由源码审阅覆盖，没有在这七案例中逐项实测。原引擎没有公开abort接口，本次也没有新增该能力。
