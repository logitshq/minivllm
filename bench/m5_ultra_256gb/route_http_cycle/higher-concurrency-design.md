# Next concurrency qualification: C16, then C32

Source-only design. Nothing here has been executed or registered, and it adds no throughput–latency point.

The frozen `route_decode_graph/candidate.py` (`6531be25…525c3`) accepts **GPU decode batch B1–8**, used length257–1536, and physical KV capacity at least1536. It chooses bound1023 below used1024 and bound1536 thereafter. Its `integration.py` dispatch covers both current and ahead decode through one `decode_model` entry. B>8 currently falls back to eager inside the long candidate; increasing HTTP concurrency alone therefore does not extend compiled coverage. The frozen `http_server_v2.py`, capture/qualification factories and `pareto_realistic/http_replay.py` also explicitly restrict this registered HTTP workload to C1/C8. Keep these sources and their existing evidence unchanged.

HTTP concurrency C counts requests between actual POST and SSE DONE. GPU B is the independently reconstructed decode row count at a scheduler step; prefill, arrivals, ahead consumption and retirement can make B smaller than C. Report both the half-open POST→DONE peak and the decode-B histogram, plus actual compiled/fallback calls per B and selected bound. C16 with only B<=8 observed is not B16 qualification, and a declared C without observed overlap is insufficient.

Use this sequence rather than launching C32 immediately:

1. Finish the present C1/C8 route-ON capture/replay and its independent numerical, resource and restoration checks. Do not transfer the old37-request/42-parameter-call prerequisite into a claim that the new HTTP history passed.
2. For C16, make a separately pinned default-OFF candidate/entry with an explicit expanded B domain. Start with a full-model B16 numerical canary on independent identical input/cache copies; then cover newly admitted B9–16, the used1023/1024 transition, mixed row lengths, parameter replacement, and current/ahead state transitions.
