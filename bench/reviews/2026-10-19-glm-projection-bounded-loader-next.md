# GLM projection-bounded loading: current status and smallest next change

Source-only review during E055. No GPU/backend import, test execution, model payload read, hash, service operation or network request. The new loader below is a proposal, not an implemented or qualified candidate.

The repo has **no projection-bounded loader implementation yet**. The smallest useful implementation is a default-OFF replacement for the official loader's final whole-parameter evaluation. Keep all official sanitizers and their original `mx.stack` operations unchanged; evaluate one resulting projection only after sanitizer frames and strict parameter loading have returned. This avoids rewriting the GLM container, MTP wrapper and quantization logic merely to remove Python aliases.

## Exact ownership seam

Let `P=.artifacts/omlx-baseline/.venv/lib/python3.13/site-packages` under the repo. The installed sources inspected here are the same paths recorded in the earlier review; no new SHA was computed during E055.

- `P/mlx_vlm/utils.py:965–967` gathers shard arrays into `weights`. `:1075–1090` completes the official sanitization passes. `:1093–1142` applies the original quantization aliases and module recipes; `:1176–1178` drops only officially absent modules and performs strict `model.load_weights`. `:1191–1192` then evaluates the complete model parameter tree in one call.
- `P/omlx/patches/mlx_vlm_glm5_next_compat/vendor/mlx_vlm/models/glm5_next/glm5_next.py:129–166` keeps original `weights`, `remapped`, `lang`, `vis` and `other` in the container frame while language sanitize runs.
- `P/omlx/patches/mlx_vlm_mtp/glm5_next_vlm_runtime.py:835–890` additionally keeps `weights`, `backbone`, `nextn` and MTP block dictionaries. The real MTP path retains layer45 and runs its original sanitizer as layer0 before rebinding to `mtp.0.*`; MTP is not simply removed when speculative decoding is OFF.
- `P/omlx/patches/mlx_vlm_glm5_next_compat/vendor/mlx_vlm/models/glm5_next/language.py:2020–2087` preserves the original router dequantization, convolution transforms and FP32 casts. `P/mlx_lm/models/deepseek_v32.py:512–535` builds another dictionary and stacks each suffix with experts in numeric order 0…287, projection order gate/down/up and suffix order weight/scales/biases.

An eager wrapper around the innermost `mx.stack` would run while these outer frames still own raw input arrays. Popping only DSV32's local entries cannot release their other aliases. After the loader has reassigned the sanitized dictionary and returned from strict `load_weights`, those sanitizer frames are gone. Its remaining `weights` aliases point to the sanitized outputs; explicitly `clear`/delete that loader dictionary before evaluation, after quantization and strict loading no longer need it. The model must retain its final output arrays. Evaluation still owns the selected stack's lazy source dependencies until MLX finishes it; their actual retirement must be observed, not inferred merely from deleting Python names.

## Minimal candidate, not a new loading framework

Create a small new namespace, for example `glm_projection_materialize_v1/candidate.py`, with injected `mx` and explicit enablement. Use a source-bound private copy of the installed `load_model` function, changing only its final non-lazy evaluation block. Do not globally wrap every `mx.eval` or change the sanitizer functions. Refuse unsupported model/config/source identities, offload, adapters and non-strict loading.

1. Preserve ordinary filename loading of the **original 62-shard checkpoint**, actual official container/MTP sanitizers, original expert order and every original arithmetic operation. Keep quantization recipes, dtypes, vision path, MTP contents and strict key/shape checks. This arm tests materialization scheduling; do not combine it with file-like IO, F_NOCACHE, allocator tuning or repacking.
2. After strict loading, clear/delete the loader's sanitized-weight dictionary. Build a deterministic schedule containing only final parameter handles. For each backbone layer3…44, then the actual retained MTP block, evaluate its gate/down/up projection's weight/scales/biases together. Call `mx.eval`, synchronize, release the temporary group references, then clear retired cached buffers before advancing. Evaluate remaining parameter arrays in bounded individual groups; ensure complete, exactly-once parameter coverage without leaving lazy work hidden until the first request.
3. Preserve final `model.eval()`/return behavior and later official gate/up fusion. Emit scalar stage records only: group key, logical payload size, active/cache/peak/guideline and elapsed time. Do not keep arrays in logs, closures or a second reference model. The existing cold owner provides raw free/file-backed/compressor/swap observations and settled recovery; its thresholds remain unchanged.

For the reviewed original shapes, a complete gate/up projection group is **1.265625 GiB**, and down is **1.546875 GiB**, including packed weight, F16 scales and F16 biases across all288 experts. The backbone totals171.28125 GiB; MTP adds its original layer. The 1.546875 GiB figure is a group payload bound, not a process or physical-memory bound. Pending lazy graphs, other parameters, cache, driver allocation and OS page cache remain outside it. Evaluation should stop at the first existing guard violation, retain the failure, and recover the original service.

The smallest implementation gap is therefore the **one late evaluation seam plus an ownership-aware group scheduler**. A tiny scalar gate cannot certify that MLX detaches consumed graph inputs; this needs actual runtime evidence. The existing sources do not prove that delayed evaluation will fix E039's page-cache pressure. If this control still fails, use the separate cached-file-like versus uncached-file-like arm motivated by E041; do not silently fold it into this candidate or relax the cold-load zero-swap gate.

## Minimum checks before another full load

CPU tests should exercise the single exact source edit, original sanitizer output key/shape/dtype/byte equality on the existing packed fake fixture, numeric expert order including MTP, unchanged quantization aliases, full schedule coverage, release of outer dictionary aliases before the first mocked evaluation, and cleanup on evaluation failure. Default/import paths must not import MLX or touch devices. These are mechanism checks, not real memory proof.

After E055 closes, a separate tiny actual MLX qualification can compare the unchanged stock stack against the scheduled path in original bytes while observing dependency retirement. A bounded real projection check can then use existing header/part references to compare stacked bytes without holding a second full model. Only after those gates should the registered original-service cold-stop/load/four-request/recovery diagnostic be prepared against the current predecessor. Load success, post-warm residency, exact inference qualification and formal throughput/latency remain separate gates.

## Correction: the public lazy-load seam is smaller

Further source inspection after the review above found that copying or editing `load_model` is unnecessary. For the exact ordinary non-offload checkpoint, its `lazy` value only skips the final parameter `mx.eval` (offload has separate behavior and must be refused). `model.eval()` at1195 sets training flags only: `mlx/nn/layers/base.py:606–611` returns `train(False)`, not tensor evaluation.

`mlx_vlm/utils.py:1274–1328` already exposes `load(..., lazy=True, strict=True)`. It calls the unchanged `load_model`, initializes image/processor objects, and returns `(model, processor)`. An explicit wrapper can call that original function once, then perform the projection schedule before returning the same tuple. Both loader and sanitizer frames are naturally gone: no source-copy, AST rewrite, global `mx.eval` hook, or manual mutation of the old weight dictionaries is needed. This replaces the source-copy proposal above. Processor construction now occurs before materialization; failures must propagate rather than falling back to another loader.

The actual oMLX GLM call imports `mlx_vlm.utils.load` at `omlx/engine/vlm.py:2050`, applies the existing pre-load MTP patch before instantiation, and calls the ordinary loader in its MLX executor at2154–2175. GLM currently receives no lazy flag unless offload is enabled. A child-scoped callable replacement at that seam can preserve all outer engine behavior; it must record the new inner `lazy=True` route and refuse adapters, custom quantization, offload, extra download/revision options and non-strict calls. `utils.py:912–917` shows why simply passing strict=True is insufficient for an offload directory: its `offload_index.json` overrides strict toFalse.

Keep the later official `omlx/utils/model_loading.py:1390–1447` materialization intact, reached by `engine/vlm.py:2274–2276` on the same executor. Besides parameter-tree arrays, it scans plain helper objects and underscore-held arrays. Its actual `_MATERIALIZE_EVAL_CHUNK` is **8** (`model_loading.py:23`). Our parameter scheduler must not claim to replace that extra-buffer coverage. Later gate/up fusion at2294–2318 also remains unchanged.

The new source-only prototype is [glm_projection_materialize_v1](../m5_ultra_256gb/glm_projection_materialize_v1/README.md): injected default-OFF wrapper, complete projection-key scheduler and seven unexecuted CPU mechanism tests. It does not install itself or provide a registered device path. An explicit `admit` callback is required for the future owner's source/model/config checks; the prototype does not mistake that interface for completed qualification. There has been no backend import, test/device execution or model payload/hash work in this preparation.
